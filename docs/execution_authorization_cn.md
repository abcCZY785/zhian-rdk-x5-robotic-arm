# 自然语言到机械臂执行的确认边界

检查日期：2026-10-16。基线：`2769ecef70ee84e056a33b40b9bc5bf9aea43eb6`。

本次仅加固软件中的执行确认链。没有连接真实机械臂、相机或串口，没有调用付费模型。
软件测试通过不代表真实机械臂的安全验收。

## 检查结论

| 环节 | 检查结果 | 本次处理 |
| --- | --- | --- |
| 自然语言规划 | `task_planner` 仅返回任务；`text_experiment_assistant` 仅写规划结果 | 保持规划与执行分离 |
| 任务解析 | 原先用 `bool(...)` 转换 `confirm_before_run`，字符串 `"false"` 也会成为真 | 必须显式提供布尔值 `true`，拒绝缺失、`false`、数字、字符串和 `null` |
| HTTP `/plan` | 自然语言分支传 `--build-only`；模板分支不调用执行入口 | 路由决定模式，忽略请求体的模式；规划不向下游传递执行确认 |
| HTTP `/execute` | 原先未校验请求级确认，进入该路由后自动添加 `--confirm` | 先检查顶层 `confirm: true`，缺失或 `false` 返回 403，类型错误返回 400 |
| 两条管线 | 自然语言分支原先将所有非 `plan` 模式当作执行 | 共用模式白名单与确认校验；直接调用管线也默认拒绝执行 |
| 自然语言 CLI | 原有 `not build_only and confirm` 判断 | 保留；无 `--confirm` 不调用执行入口；`--build-only` 优先 |
| 抓放任务入口 | 只有收到 CLI `--confirm` 才向串口主控传递同名参数 | 保留 |
| 串口主控 | 未确认时在创建 `V7SerialClient` 前返回 | 保留现有底层保护，并用替身验证 |

服务仍绑定 `127.0.0.1`。这些代码事实不足以认定服务已对公网开放或存在可远程利用的漏洞。
`web/` 当前只有迁移说明，没有可核验的网页实现，无法据此判断原有前端是否有确认弹窗。

## 两个字段的不同含义

- `task.confirm_before_run: true`：任务数据必须遵守“执行前需要确认”的策略；它可以由模型或模板产生，**不能授权执行**。
- 请求顶层 `confirm: true`：调用方对**当前这一条执行请求**的明确确认；不会从上次请求、最近状态、任务数据或自然语言中继承。

HTTP 层与两条管线入口都检查确认。模式仅允许 `plan` 或 `execute`，未知模式直接报错。
只有执行模式且严格布尔值确认为真时，桥接层才添加底层所需的 `--confirm`。
不使用 `bool(value)`，所以 `1`、`1.0`、`"true"`、`"false"` 均不能通过确认校验。
请求 JSON 和模型生成的 JSON 拒绝重复键，避免同一确认字段出现相互矛盾的值。

## API 调用契约与兼容性

规划请求：`POST /api/assistant/plan`

```json
{"instruction": "把左边的烧杯放到配置台右侧"}
```

只有操作人员独立确认本次任务后，调用方才应发送：`POST /api/assistant/execute`

```json
{"instruction": "把左边的烧杯放到配置台右侧", "confirm": true}
```

固定模板可用 `template_id` 替代 `instruction`，遵守相同确认规则。
不要在前端加载、规划完成、响应复制或自动重试时默认添加 `confirm: true`。
前端应先展示具体任务及运动影响，再由独立的确认操作构造执行请求。

| 输入 | `/execute` 结果 |
| --- | --- |
| 无 `confirm` 或 `confirm: false` | 403；不启动模型、视觉、构建或执行，不覆盖最近状态 |
| `confirm: "true"`、`1`、`null` 等 | 400；不启动管线 |
| 只有 `confirm_before_run: true`、嵌套确认、`confirmed: true` 或文字“已确认” | 403；不能替代顶层确认 |
| 顶层 `confirm: true` 且请求有效 | 允许进入执行管线；后续模型、定位、构建失败仍会失败 |
| 数组、标量、损坏编码、无效长度或重复 JSON 键 | 400；不启动管线 |

`/plan` 即使收到 `confirm: true` 或 `mode: "execute"`，仍仅规划；错误类型的 `confirm` 也会被拒绝。
执行过程中模型任务不符合确认策略时返回 500，且不进入真实机械臂执行入口。

有意收紧的兼容性变化：旧执行客户端必须在独立确认后增加顶层 `confirm: true`；
原来缺少 `confirm_before_run` 的模型任务现在校验失败，不能靠默认值补齐。
规则模板和内置任务模板仍保留确认策略。
相机索引要求非负整数，指令、模板 ID 和串口名称拒绝错误类型。

为使当前仓库入口可导入，本次同时修复三个入口中的旧 `lab_assistant` 包名，
以及桥接层与自然语言管线中已迁移脚本的路径；日志与运行产物统一以仓库根目录为基准。
没有修改串口运动控制算法。

## 完全离线测试

从仓库根目录运行（Python 3.11+，仅需标准库，无需安装视觉或串口依赖）：

```bash
python -m unittest discover -s tests -v
```

也可使用 `make test`。测试覆盖：

- 缺失、拒绝、伪造类型、错误位置的确认字段，以及相互矛盾的重复字段。
- 任务解析和模型输出中必须为布尔值 `true` 的确认策略，包含规则规划路径。
- 两条管线的直接调用、未知模式、正常规划及明确授权执行。
- 真实内存 HTTP 解析 → 真实规划与任务解析 → 真实 CLI 判断 → 抓放任务入口 → 模拟串口执行进程的完整软件调用链。
- `--build-only` 与 `--confirm` 同时出现仍不执行；无 `--confirm` 仅构建；规划专用助手不执行。
- 上一次规划或执行不会授权下一次请求。
- 原有串口主控：未确认时不创建串口客户端；确认后只到达被替换的客户端边界。

测试用本地样本代替模型响应、相机结果和轨迹构建产物，以模拟进程接口替代真实串口执行。
HTTP 使用内存字节流，不监听本机端口。所有输出写入临时目录。
测试为 `subprocess.Popen`、网络 socket、`urlopen`、`os.system` 和真实 `MimoClient.chat` 安装禁止调用的检查，
并在每项测试结束时核对没有尝试调用；底层测试还替换 `serial` 模块及 `V7SerialClient`。

本次结果：Python 3.12.14，**37 项测试通过，0 失败、0 错误**（另含多组参数子用例）。
这验证了软件授权分支，没有验证视觉精度、轨迹质量或实物运动行为。

## 剩余安全边界

1. **确认字段不等于身份认证。** 任何能访问服务的客户端都能自行构造 `confirm: true`。
   本次没有增加登录、访问令牌、调用者权限或可信人机确认设备；不能证明屏幕前确实有人点击确认。
   原有通配 CORS 也仍存在。本机绑定不能代替来源校验，代理、端口转发和本机恶意程序会影响可达性。
2. **确认尚未绑定不可变计划。** `/execute` 仍按原有功能重新规划、重新定位和构建，
   因此结果可能不同于此前预览；没有计划摘要绑定、一次性令牌、有效期或幂等去重。
   生产部署需要将审阅的计划、实际坐标、配置及轨迹摘要绑定到一次性执行授权，并处理重放和并发。
3. **仓库尚不构成完整部署。** `build_pick_place_task_v7.py`、原网页/URDF 资源及模型权重尚未迁入；
   部分解释器配置仍为 Windows 本机路径，需要现场部署配置。
   测试替代了这些外部组件，不能证明缺失的构建器没有硬件副作用，也不能证明真实环境已端到端可运行。
   恢复构建器后应先确认规划阶段只计算或生成文件，不发送硬件命令。
4. **本次范围是 HTTP 与自然语言链。** 直接运行其他视觉、回放、调试脚本，
   或修改本机代码/任务文件，仍受各自的确认和权限边界约束；没有完成全仓库所有硬件入口的安全审计。
   HTTP 请求大小、执行超时、请求来源控制及敏感日志也没有在本次全面加固。
5. **软件确认不替代物理保护。** 关节限位、工作空间约束、碰撞保护、急停、限力、夹具、
   标定、液体操作及人员隔离都需要独立检查和真实硬件验收。本次没有验证这些保护是否存在或有效。
